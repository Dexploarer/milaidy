## 2024-05-15 - Command Injection Risk in execSync
**Vulnerability:** Shell command injection via `execSync` with string interpolation (e.g., `execSync(\`rec -q ${tmpFile} trim 0 ${durationSec}\`)`). Although variables like `durationSec` and `tmpFile` might be generated locally and validated, passing them to a shell context via `execSync` leaves the door open for injection if the inputs were ever modified to be user-controlled.
**Learning:** `execSync` executes commands in a shell environment which parses spaces and special characters. When executing shell commands on any OS, array arguments must be used with `execFileSync` to avoid parsing. On Windows specifically, `execFileSync` inherently passes arguments as an array, eliminating the need to manually quote strings containing spaces (e.g., `audio=Microphone` is correct, `'audio="Microphone"'` causes double-escaping bugs). Additionally, `stderr` from noisy tools like `ffmpeg` should be piped to `ignore` in `stdio` settings to prevent `stdout`/`stderr` deadlocks when replacing shell redirects like `2>/dev/null` or `2>NUL`.
**Prevention:** Always use `execFileSync` (or `spawn`/`execFile`) with strict argument arrays for dynamically constructed commands instead of `execSync`. Ensure standard error buffers from child processes are either consumed or explicitly ignored if replacing shell error redirection.
